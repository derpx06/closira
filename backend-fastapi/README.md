# AssistFlow FastAPI Backend

This directory contains the Python + FastAPI migration of the AssistFlow backend.

The migration target is API and behavior parity with the Node/Express backend, including:
- Authentication and authorization
- Ticketing workflow
- Widget and human handoff flows
- RAG/chat endpoints
- MongoDB persistence behavior
- Qdrant vector integration
- Socket.IO real-time events

## 3) App Boot and Lifecycle

Boot path:
1. `run.py` starts uvicorn on `app.main:app`
2. `app.main` builds `fastapi_app`
3. Lifespan startup:
   - configure logging
   - DB ping (`test_db_connection`)
   - index bootstrap (`ensure_indexes`)
4. Routers mounted under `/api`
5. Socket.IO ASGI app wraps FastAPI at `/socket.io`

Important behavior:
- If DB is unavailable and `DB_REQUIRED_ON_STARTUP=true`, startup should fail.
- If false, app logs warning and continues.

## 5) Database Model and Index Strategy

Primary Mongo collections:
- `companies`
- `users`
- `company_roles`
- `questions`
- `api_keys`
- `knowledge_sites`
- `sitemaps`
- `tickets`
- `messages`
- `chat_sessions`
- `counters`

Index setup is handled in `app/db/indexes.py` and includes:
- unique `id`/`uuid` constraints where expected
- lookup indexes for company-scoped querying
- compound indexes for ticket/message retrieval patterns
- `chat_sessions.sessionId` unique
- legacy `sitemaps.companyId_1` cleanup

Sequence behavior:
- Numeric IDs are generated by atomic counter updates in `app/db/counters.py`
- Uses `ReturnDocument.AFTER` to preserve Node parity.

## 6) Security Model

### HTTP auth
- Bearer JWT expected in `Authorization` header.
- `require_auth` resolves:
  - `user_id`
  - `company_id`
  - `role`
- `require_admin` enforces `role == "admin"`.

### Socket auth
- Accepts token from:
  - `auth.token` (socket handshake)
  - `Authorization: Bearer ...` header fallback
- Supports:
  - agent tokens (user/company/role)
  - widget tokens (`tokenType=widget`, session+ticket context)

### Widget/chat mixed auth
`/api/rag/chat` supports:
- `x-api-key` (widget)
- Bearer token (dashboard)

## 9) RAG and Search Subsystems

### `rag_engine.py`
Current implementation includes:
- Q/A short-circuit from `questions` collection
- response generation scaffolding
- ticket escalation payload generation

### `ticket_vector_service.py`
- Qdrant ticket collection ensured on demand
- deterministic fallback embedding currently used to keep system functional without heavyweight local model setup
- search is company-scoped via payload filter

### `rag_service.py`
- `rag_chat` flow with optional auto-ticket creation
- knowledge base statistics
- knowledge-site CRUD support
- API key management under rag routes
- crawl/sitemap route support (sitemap-first behavior and codebase route extraction)
